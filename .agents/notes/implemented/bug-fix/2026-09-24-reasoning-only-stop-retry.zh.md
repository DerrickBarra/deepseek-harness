# Agent Note: 仅推理停止会在 assistant 完成前重试

Status: implemented

[English](2026-09-24-reasoning-only-stop-retry.md) | 中文

## 问题

某些推理模型会发出格式正确的终止性 `stop`，但组装后的响应只包含推理块，没有最终文本或工具调用。提供方报告成功，因此循环会把不完整的推理提交为 `assistant/message`，并将轮次作为已完成关闭。这与零内容块的 `EMPTY_RESPONSE` 不同：模型产生了输出，但该输出不是可用答案。

## 决策

当组装后的消息至少有一个块且所有块都是推理时，agent loop 将正常停止归类为不完整答案。它追加一条仅用于日志的 `step/empty-answer` 事件，其中包含轮次、步骤、尝试次数、配置的重试上限、推理字符数、512 字符后缀，以及是否会继续尝试。失败尝试不会追加 `assistant/message`，因此派生模型历史不会把不完整推理反馈给重试请求。

`reasoningOnlyStopRetries` 是非负安全整数的 agent-loop 设置，默认值为 `2`。循环在同一轮次和步骤坐标下重试确切步骤。重试耗尽会抛出 `EMPTY_ANSWER` LLM 失败，并将轮次作为错误关闭。带文本的停止、工具调用结束和 `max-tokens` 输出保持原有行为。

`step/empty-answer` 事件是持久事件，因为异常与重试决定必须能在回放后保留，并支持事件诊断。原始分片仍是完整输出的来源；该事件只存储有界后缀。

## 考虑过的替代方案

**在每个适配器中归类响应。** 适配器负责将零内容块响应从 wire 事实转换为 harness 归类，但仅推理的不完整性是适配器与模型共享的语义不变量。重复实现检查会造成保护不一致，并要求每个适配器理解 assistant 输出是否可用。

**复用 `EMPTY_RESPONSE`。** 该响应并非空响应，现有重试策略也刻意把推理视为内容。复用该代码会抹去传输／提供方空响应与模型在产生答案前停止之间的区别。

**在重试前提交推理消息。** 这样可以为每次提供方调用保留完成锚点，但派生历史会回放触发恢复的同一段不完整推理，并可能放大重复循环。原始分片与 `step/empty-answer` 在保留证据的同时，不会让失败尝试对模型可见。

**重试但不记录持久事件。** 这样可以缩小会话事件集合，但重新加载后重复失败将不可见，操作人员也无法区分慢请求与有界恢复。

## 后果

瞬时的提前停止可以在无需用户干预的情况下恢复，持续失败则成为明确的轮次错误，而不是虚假成功。每次重试都会再消耗一次提供方请求。用量分片保持持久，token 投影会观察它们；步骤级计时和完成计数仍描述最终可用的完成结果，而不是每次被拒绝的尝试。若模型有意只返回推理而不提供答案，系统会重试并最终失败；需要这种行为的部署可以把重试次数设为零。
